# 「今天吃什么」V1.0 产品复盘

## 1. 复盘说明

- 版本：V1.0 Portfolio MVP
- 复盘日期：2026-08-26
- 版本状态：已公开发布，当前稳定基线
- GitHub：[1335389202-create/what-to-eat](https://github.com/1335389202-create/what-to-eat)
- Live Demo：[今天吃什么](https://1335389202-create.github.io/what-to-eat/)

本复盘记录 V1.0 实际完成了什么、哪些判断经过了哪种验证、哪些仍是假设。它不是宣传稿，也不把自动化测试通过等同于真实用户价值已经成立。

## 2. V1.0 产品目标

V1.0 的目标不是实现最初 PRD 中的完整产品，而是用公开可访问的 Portfolio MVP 验证一个最小、完整、可解释的居家做饭闭环：

> 用户录入家中食材，在少量条件约束下获得带随机性的合理推荐，查看结构化菜谱，确认制作并安全更新本地库存。

目标包含三层：

1. **产品层**：证明“可自定义的吃饭盲盒”不是普通菜谱搜索，并能优先利用库存减少浪费；
2. **体验层**：跑通库存四态、盲盒揭晓、菜谱到制作确认、可编辑扣减和异常恢复；
3. **Portfolio 层**：形成可公开部署、可读、可测试、无后端依赖的完整作品。

## 3. 实际完成

### 3.1 已实现用户闭环

```text
首页
→ 食材库存
→ 推荐条件
→ 盲盒抽取
→ 推荐结果
→ 菜谱
→ 制作确认
→ 可编辑库存扣减
→ 原子更新
→ 更新后首页
```

用户可以：

- 无需登录直接使用；
- 手动添加、编辑同名多批次食材；
- 记录精确、约数或未知数量；
- 设置 1/2/4 人、午餐/晚餐、结果形式、菜系、荤素、辣度和最长时间；
- 在“尽量用库存”和“允许少量补买”之间切换；
- 在合格候选中随机抽取；
- 查看满足、可能满足、不足、未知四种库存数量状态；
- 查看结构化 Mock 菜谱、人数自适应需求量和营养估算；
- 进入扣减预览，修改或跳过批次扣减；
- 只有最终确认后才一次性更新 LocalStorage；
- 在写入失败时保留库存和编辑内容；
- 使用显式 Reduce Motion 控件并继承系统减少动态效果偏好。

### 3.2 已实现产品资产

- `PRD.md`：完整产品需求事实源，范围大于 Portfolio MVP；
- `design-document.md`：UX 架构、页面体系、状态与响应式原则；
- `prototype-spec.md`：24 Frame、五条核心流程、固定样例、测试任务与验收；
- `prototype/`：独立低保真过程资产；
- Portfolio MVP：原生 HTML/CSS/JavaScript ES Modules；
- 20 道中西餐 Mock 菜谱；
- LocalStorage 版本化数据；
- GitHub Public Repository、README、截图、LICENSE 与 Pages CI/CD。

### 3.3 明确未实现

以下能力从未属于 Portfolio MVP 已实现范围：

- 登录、手机号验证码和云同步；
- AI 图片识别或 AI 推荐；
- 云数据库、正式后端和多设备数据；
- 地图、商圈、真实餐厅、菜单和外出用餐完整流程；
- 第三方营养、价格或食品安全数据；
- 完整随机菜单采购闭环；
- 收藏、家庭共享、长期个性化与生产级推荐算法。

它们继续属于 Roadmap，不能因为原始 PRD 曾经描述过就写成 V1.0 已完成。

## 4. 核心设计决策

| 决策 | V1.0 选择 | 收益 | 已知代价 |
|---|---|---|---|
| 核心范围 | 只实现居家做饭闭环 | 形成小而完整的可演示产品 | 无法覆盖最初设想的外出场景 |
| 技术形态 | 原生 HTML/CSS/JS ES Modules | 无构建步骤、依赖少、静态部署稳定 | 视图集中在单个 `app.js`，后续复杂度上升时需控制维护成本 |
| 数据 | LocalStorage 单设备存储 | 无后端即可真实持久化和刷新恢复 | 无账号、备份、同步或跨设备能力 |
| 内容 | 20 道结构化 Mock 菜谱 | 候选可控、可测试、能覆盖多种状态 | 菜谱与营养不代表完整或权威数据库 |
| 推荐 | 硬条件过滤→库存匹配→候选→透明加权随机 | 可解释、可复现、不伪装 AI | 个性化与真实效果尚未验证 |
| 库存状态 | 满足/可能满足/不足/未知 | 区分数量事实与不确定性 | 用户是否能在真实使用中正确理解仍需可用性测试 |
| 库存更新 | 查看菜谱不扣减，确认制作后预览并原子提交 | 防止静默改库存，失败可恢复 | 比“点击完成即扣减”多一步操作 |
| 临期机制 | `expiresOn` + `useSoon` 驱动临期显示、加权和批次顺序 | 原型叙事简单、容易制造减浪费示例 | 用户通常不知道准确到期日，且文案容易被理解为安全判断 |
| 动效 | 短盲盒 + 可跳过 + Reduce Motion | 保留仪式感而不阻塞任务 | 趣味性是否提升留存没有真实数据 |
| Scope Freeze | 新想法进入 Roadmap | 按期形成稳定 Demo，避免 V1.0 无限膨胀 | 部分原 PRD 首版设想被推迟 |

## 5. 原型验证复盘

浏览器低保真原型实现了 24 个既定 Frame、14 个页面/状态和 10 个 Overlay/Bottom Sheet，并通过 76/76 自动化验收。验证覆盖：

- 五条核心流程可点击；
- 四种库存数量状态；
- 盲盒与 Reduce Motion；
- 菜谱→制作→扣减；
- 无结果恢复；
- 扣减失败保护；
- 固定样例数值链与补买金额。

需要准确说明其证据强度：

- **已经证明**：原型实现与 `prototype-spec.md` 的结构、连线、样例和技术验收一致；
- **没有证明**：真实用户能无提示理解全部状态、会持续录库存、会因为盲盒更愿意使用，或会实际减少食物浪费；
- **后续需要**：小样本可用性测试、真实使用行为和访谈，而不是继续增加自动化断言来替代用户证据。

## 6. 自动化测试复盘

V1.0 建立了分层测试，而不是只检查页面能打开：

| 测试层 | 结果 | 覆盖重点 |
|---|---:|---|
| Prototype 独立基线 | 76/76 | Frame、流程、状态、样例数值、异常恢复 |
| Portfolio MVP | 82/82 | 存储、推荐、扣减、端到端闭环、响应式、无障碍与运行时错误 |
| HTTP 与 Pages 子路径烟测 | 13/13 | ES Modules、资源路径、Hash 导航、刷新与 LocalStorage |
| 发布预检 | 13/13 | 仓库包装、相对路径、workflow、secret/手机号扫描 |

测试带来的真实收益：

- Scope Freeze 后可以持续修改视觉和发布包装而不破坏核心闭环；
- 原子扣减和失败回滚有可重复证据；
- GitHub Pages repository subpath 问题在发布前被覆盖；
- Prototype 与生产 Demo 分离，低保真基线未被 Portfolio 视觉升级破坏。

测试的边界：

- 主要使用固定 Mock 数据；
- 浏览器组合和长期 LocalStorage 演进覆盖有限；
- 没有真实数据迁移历史；
- 没有食品安全、营养准确性或真实推荐效果验证；
- 自动化不能替代用户访谈和行为数据。

## 7. MVP Scope Freeze 复盘

Scope Freeze 是 V1.0 能完成的重要原因。开发阶段明确不引入 React/Vite、后端、登录、AI、地图、外部 API 或生产级推荐算法，并优先复用已验证原型。

做得好的地方：

- 功能边界具体，Roadmap 项没有因“实现方便”提前进入；
- 交付速度、稳定性、可维护性优先于技术炫技；
- 低保真过程资产与公开 Demo 代码分离；
- 每步通过验收后才进入下一步。

可以改进的地方：

- V1.0 的“临期”逻辑在原型阶段为固定样例服务，进入真实 Demo 后缺少一次语义风险复核；
- 根 PRD 的完整首版与实际 Portfolio MVP 范围不同，后续读者容易把“批准需求”与“已实现”混为一谈；
- 版本复盘与迭代文档在发布时尚未建立，产品决策主要散落在阶段计划和 README 中。

## 8. 部署结果

V1.0 已完成：

- 公共 GitHub 仓库；
- GitHub Pages + GitHub Actions 自动部署；
- 正式 Live Demo；
- 仓库子路径兼容；
- README 的本地 HTTP 启动、测试、Roadmap 和限制说明；
- 无运行时 secret、API Key、手机号或本机绝对路径。

发布方式适合当前静态 MVP。V2.0 不需要改变 Pages workflow，也不需要引入构建工具或后端。

## 9. 当前限制

### 9.1 产品证据

- 尚无真实用户样本、漏斗数据、留存数据或减少浪费的量化证据；
- “今天吃什么”的高频价值、库存录入负担和盲盒趣味性仍是假设；
- 没有验证购买日期录入是否比临期标记更自然。

### 9.2 数据与内容

- LocalStorage 只在当前浏览器和设备有效；
- Mock 菜谱覆盖有限；
- 营养、价格和时间是演示估算；
- 用户清理浏览器数据后无法恢复；
- Schema v1 只演示过 v0→v1 迁移，没有真实向后兼容压力。

### 9.3 体验与技术

- `app.js` 集中承担渲染、事件和业务编排，V2.0 应做小范围抽取但不重构框架；
- 食材录入仍需要用户主动维护；
- 重置演示数据是即时操作，对已有本地数据缺少二次确认；
- “临期”文案与预期到期日存在食品安全暗示风险；
- 没有真实分析事件，指标目前只能定义，不能观测。

## 10. V1.0 暴露出的下一轮问题

按优先级排序：

1. **语义风险**：`expiresOn/useSoon` 容易让产品看似能判断食品是否过期；
2. **迁移风险**：公开版本已有 LocalStorage v1，字段变化必须保护现有库存与 pending deduction；
3. **解释不足**：推荐理由只说“临期”，没有说明用户实际记录了什么、为什么加权；
4. **信息层级**：首页和库存页把“临期”作为强状态，未区分购买时长与数量满足度；
5. **Demo 可持续性**：固定 2026 年日期会随着真实日期推移失去合理语义；
6. **指标缺失**：还不能回答推荐是否帮助用户完成决策、再来一次代表趣味还是不满意；
7. **过程可发现性**：V1.0 的产品决策、验证边界和版本演进尚未从 README 直接进入；
8. **真实用户验证缺失**：自动化完整，但没有真实用户行为和口述证据。

## 11. 关键经验

- 先冻结一个完整闭环，比在 V1.0 同时实现居家、外出、登录和 AI 更有效；
- 原型验收与生产验收应独立保留，避免视觉升级覆盖过程证据；
- 数据写入功能必须先定义失败后的数据状态，再设计成功动画；
- 随机推荐必须在合格候选中发生，并能解释为什么候选合格；
- Portfolio 质量不仅是视觉，还包括范围诚实、测试、部署和已知限制；
- 自动化通过说明“实现符合已知规格”，不说明“规格已经被真实用户证明正确”；
- 已公开产品的数据语义变化必须先规划 Schema Migration 和变更传播，不能只改界面文案。

## 12. 复盘结论

V1.0 已完成其 Portfolio MVP 目标：一个公开、稳定、可操作、可解释并有自动化保护的居家做饭闭环。它没有完成完整商业产品，也没有证明真实留存或减少浪费效果。

V2.0 应保持现有流程与技术基线，优先修正购买时长语义、保护本地数据迁移、增强推荐解释，并建立可持续的版本文档和验证口径。登录、AI、地图、外出和真实第三方数据不应借此次迭代进入范围。
