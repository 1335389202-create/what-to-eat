## 2. Problem

V1.0 使用“预计到期日 / 尽快食用 / 临期”驱动库存优先级。这个机制存在输入可信度问题：普通用户通常记得何时购买，却未必知道每种新鲜食材的准确保质期。应用在缺少可靠来源时使用“临期”，容易让优先使用建议看起来像食品安全结论。

V2.0 要解决的不是更精确地猜测过期，而是把产品事实收缩到应用能够诚实表达和计算的范围。

## 3. Hypothesis

核心假设是：

> “购买日期”比“预计到期日”更容易由用户回忆或记录；由此动态计算“已购买天数”，可以提供有用的优先使用提示，同时避免假装掌握食品安全事实。

因此产品机制改为：

```text
购买日期
→ 已购买天数
→ 优先使用提醒
→ 可解释推荐与较早批次优先建议
```

该假设包含两层尚待用户验证的判断：用户愿意维护购买日期，以及 5 / 7 天阈值足以改善决策而不会制造新的误解。

## 4. What Changed

### 4.1 产品语义

- 库存批次新增可选 `purchasedOn`；购买日期未知时保持未知。
- 0–4 天为普通状态，5–6 天提示建议优先使用，7 天及以上提示已购买较久。
- 所有相关界面明确：购买时长不等于保质期，也不代表食品安全判断。
- 运行时不再使用“临期 / 预计到期 / 尽快食用”作为活跃产品事实。

### 4.2 推荐与解释

- 5–6 天为候选增加 `+2`，7 天及以上增加 `+3`。
- 同一候选只采用一个最高档加分，多个较久食材不叠加放大。
- 推荐理由指向实际贡献的食材、批次和购买天数。
- unknown、invalid、future 或数量未知批次不产生购买时长加权。

### 4.3 制作与扣减

- 已知购买日期按从早到晚排序；未知、无效和未来日期稳定排后。
- 排序只是建议，用户仍可编辑或跳过任一扣减项。
- 扣减继续采用副本校验与单次写入，失败时库存零变化且保留编辑。

### 4.4 数据迁移与恢复

- LocalStorage 文档从 Schema v1 迁移到 Schema v2，主 key 为兼容历史继续沿用。
- 写入新文档前保存原始 v1 payload 的独立备份。
- `expiresOn / useSoon` 仅进入 `legacy`，不反推 `purchasedOn`。
- 备份、主写入或回读失败时阻止覆盖；损坏数据也不会被自动重置。
- `daysSincePurchase` 不持久化，始终按本地自然日动态计算。

## 5. What Went Well

### Artifact-driven change propagation

同一变化依次落到 PRD、UX 文档、Prototype Spec、实施计划、运行时、测试、README 与 CHANGELOG。旧语义没有只在界面上改名，而是同步处理数据、推荐、扣减、恢复和发布证据。

### Migration-first

Schema v1 → v2 的备份、无损迁移、失败回滚和恢复路径先于界面完成。这使生产 Gate 能直接验证最危险的用户数据路径，而不是只确认新用户可用。

### Test Gate

冻结自动化门禁为 254/254：主项目 151、Prototype 76、部署 13、Release Preflight 14；README 链接另有 14/14。上线后又执行 13/13 基础部署 Smoke 和 37/37 专项生产验证。

### Feature Branch 与 Release Gate

所有 V2.0 改动保留在 `feature/v2.0-purchase-age`，人工 Release Gate 通过后才创建 PR。标签直到真实 Pages 上的迁移、Fresh V2 和完整扣减闭环全部通过后才创建，并指向实际生产提交而不是旧 RC。

## 6. What Was Difficult

### 旧字段必须“保留但失效”

直接删除旧字段会失去审计与恢复信息，直接复用又会制造错误事实。最终采用 `legacy` 保存原值、活跃模型不读取的边界，并为不推断购买日期增加专门测试。

### 动态自然日比固定样例更难测试

演示日期必须相对初始化日生成，计算要处理月末、年末、闰年、本地午夜、future 与 invalid。固定截图和可重复断言之间需要额外夹具设计。

### 生产验证需要区分产品错误与测试错误

线上专项脚本最初出现 Hash 路由等待和人数夹具错误：一人份只消耗 T-01，而跨批次数值链要求两人份。修正等待与测试条件后 37/37 通过，业务代码无需修改。这提醒我们，失败首先是证据，需要定位后才能归因。

### PR 没有独立 Checks

仓库当前没有针对 Pull Request 事件的独立 CI Checks。合并前依赖完整本地门禁，合并后由 Pages workflow 验证部署。这次流程安全完成，但未来若协作者增加，PR 级自动检查会比只在发布者环境运行更稳健。

## 7. Evidence

### 自动化测试证明了什么

- Schema v1 能无损迁移、备份并保护失败路径；Schema v2 加载幂等。
- 自然日边界、+2 / +3、最高档不叠加、unknown / future 不加权符合冻结规则。
- 推荐硬条件、四态、解释、补买预算、近期降权和随机候选边界可重复验证。
- 较早批次排序、用户编辑、失败保护与原子扣减符合实现约束。
- 320 / 390 / 768 / 1440 响应式、触控区、键盘焦点和 Reduce Motion 没有已知回归。
- Prototype 76/76 保持不变，V2.0 没有破坏过程资产基线。

### Production Smoke 证明了什么

- GitHub Pages 在仓库子路径加载 CSS、ES Modules 和内部 Hash 导航，无 404 或 console error。
- 人工构造的非个人 Schema v1 数据在线上被识别、备份并升级，数量和批次保持不变，购买日期未被虚构。
- 全新浏览器直接初始化 v2，并展示动态 5–6、≥7 和 unknown 状态。
- 正式模块在线执行 +2 / +3、不叠加以及 unknown / future 不加权。
- 两人份流程按 T-01 → T-02 建议扣减；编辑 T-02 为 100g 后，失败路径库存零变化，成功提交后剩余 120g，刷新仍保留。
- 390px、1440px、LocalStorage 与显式 Reduce Motion 在线上正常。

### 证据没有证明什么

这些验证没有证明用户愿意每天维护购买日期，也没有证明提醒阈值、权重或文案改善了真实决策，更没有证明产品实际减少了食材浪费。

## 8. Remaining Unknowns

- 用户是否愿意维护购买日期；忘记填写时是否会回补？
- 5 / 7 天阈值对不同食材是否过于粗糙？
- `+2 / +3` 是否真的改善选择，还是只改变抽取概率？
- 用户是否真正理解“购买时长 ≠ 保质期 ≠ 食品安全”？
- 提醒是否帮助用户更早使用库存，而不是增加焦虑或直接丢弃？
- 用户是否能理解推荐理由与随机性的关系？
- 产品是否真实减少食材浪费；应如何定义和收集证据？

## 9. Next Iteration Candidates

以下只记录候选，不构成 V2.1 或 V3.0 承诺：

- 进行小范围真实用户任务测试，观察购买日期填写、迁移提示理解和推荐理由复述。
- 在不改变安全边界的前提下测试日期录入的轻量化方式与“未知”恢复路径。
- 研究阈值是否应按食材分类配置，但不在缺少数据时自动推断。
- 为 PR 增加独立自动化 Checks，降低发布者本地环境依赖。
- 定义“减少浪费”的可测指标及最低隐私数据方案。

## 10. Recommendation

当前推荐先进行真实用户测试，而不是直接决定 V2.1 或 V3.0。版本方向应由购买日期维护意愿、阈值理解、推荐采纳与浪费变化的证据决定。
