# 「今天吃什么」V2.0 产品迭代计划

## 0. 文档信息

- 版本定位：V1.0 Portfolio MVP 的增量迭代
- 文档状态：待批准，尚未进入 Implementation Planning
- 规划日期：2026-08-26
- 实施基线：当前公开的原生 HTML/CSS/JavaScript + LocalStorage V1.0
- 主要主题：从“临期食材”迁移到基于购买时长的“优先使用提醒”

本计划描述产品需要改变什么、为什么改变、如何验证和何时可以发布。它不修改生产代码，不选择新框架，不创建后端，也不是 Implementation Plan。

## 1. Executive Decision

V2.0 保持 V1.0 的核心流程、库存数量四态、盲盒体验、原子扣减、LocalStorage 与静态部署架构不变。迭代重点是：

1. 用可选的 `purchasedOn` 替代用户难以准确提供的 `expiresOn`；
2. 将 `daysSincePurchase` 作为实时派生值，不持久化；
3. 用四档购买时长状态替代“临期/尽快食用”语义；
4. 将临期加权替换为透明的购买时长加权；
5. 对 LocalStorage schema v1 做可回退、幂等的 v2 迁移；
6. 更新首页、库存、结果、扣减、测试和公开说明中的全部传播面；
7. 建立 V1.0→V2.0 的版本文档和未来指标定义。

## 2. Problem

V1.0 使用 `expiresOn`、`useSoon`、“临期食材”和“优先使用临期食材”。这套规则在固定原型样例中容易理解，但放到真实录入场景存在三个问题：

### 2.1 用户输入不可靠

新鲜食材通常没有用户能确认的准确过期日期。包装、开封、冷藏、温度和食材状态都会改变可食用时间。要求用户填写 `expiresOn` 会增加录入负担，也可能产生虚假精度。

### 2.2 产品语义越界

“临期”“到期”容易被理解为应用知道食材是否安全。当前产品没有食品安全数据库、保存条件、包装信息或专业判断能力，不能从一个日期给出安全结论。

### 2.3 推荐解释不够具体

V1.0 推荐理由只说明“临期”，没有告诉用户该判断来自何种输入、持有了多久、是否只是提醒。固定 `useSoon` 加权也无法反映时间自然变化。

### 2.4 已发布数据需要兼容

V1.0 已公开使用 LocalStorage schema v1。V2.0 不能把未知语义的数据强行转成购买日期，也不能因校验失败重置用户库存。

## 3. Evidence

### 3.1 当前产品逻辑发现

- `src/storage.js` 的 schema v1 批次字段包含 `expiresOn` 与 `useSoon`，没有 `purchasedOn`；
- `src/recommender.js` 为含 `useSoon` 批次的候选固定增加权重，并生成“临期”理由；
- `src/deduction.js` 先按 `useSoon`、再按 `expiresOn` 排序批次；
- `src/app.js` 在录入、首页、库存、推荐理由和扣减预览中直接使用“预计到期”“临期”“尽快食用”；
- README、PRD、UX Design 与 Prototype Spec 也有相同语义，说明这是跨层变更，不是单个 Label 修改；
- storage 测试目前只覆盖 v0→v1，没有已发布 schema 的真实升级回归。

### 3.2 Prototype 验证证据

- 24 Frame 和 76/76 验收证明临期提示在既定样例、流程和扣减预览中实现一致；
- 原型已经验证“优先批次只是建议，用户可编辑，最终确认后才扣减”的结构，可直接继承；
- 原型没有真实用户访谈结果，不能证明用户会准确填写到期日，也不能证明“临期”不会被误解为安全判断；
- 数量四态描述“相对菜谱需要量是否足够”，与购买时长正交，不应因本次迭代被重做。

### 3.3 用户提出的新需求

用户明确要求 V2.0：

- 使用 `purchasedOn` 和 `daysSincePurchase`；
- 采用 0–4、5–6、7+、未知四档；
- 将“临期食材加权”替换为“购买时长优先权重”；
- 推荐理由必须给出具体食材和天数；
- 不输出过期、不安全、不能食用等结论；
- 设计 LocalStorage Schema Migration，保护 V1.0 数据。

### 3.4 Benchmark 启发

- 阶段 Gate、版本复盘、P0/P1/P2、研究/迭代/工作流分层适合采用；
- 指标需要分类，但没有真实数据时不能填写实际值；
- README 应提供产品过程入口，但不能与实际仓库结构漂移；
- 历史版本需要保留，但不需要复制整份 HTML 或用 iframe 强耦合 PRD 与 Prototype。

详见 [Benchmark Review](../research/benchmark-review.md)。

### 3.5 尚未通过真实用户验证的假设

以下均是待验证假设，不是事实：

- 用户更容易回忆购买日期，而不是预计过期日；
- 5 天与 7 天分档符合用户直觉；
- 购买时长解释会提高推荐信任；
- 增加优先使用权重会提高相关食材实际消耗率；
- 用户愿意为更多库存批次补充购买日期；
- 首页提醒能促进决策，而不会引发食品安全焦虑；
- 推荐中的“再来一次”主要代表趣味探索，而不是首次推荐不满意。

## 4. Goals

### G1. 纠正产品语义

让用户明确应用只展示购买时长和日常提醒，不判断食材是否过期或安全。

### G2. 保持减浪费价值

在硬约束和库存数量判断不变的前提下，让持有较久且有明确购买日期的食材更容易进入推荐结果。

### G3. 提升解释性

结果页能够回答：“哪种食材、已购买多少天、为什么本次被优先考虑”。

### G4. 保护已发布数据

V1.0 用户升级后库存、条件、偏好、最近推荐和未提交扣减不丢失；旧字段不被误转成新语义。

### G5. 保持增量与稳定

不改变框架、部署、核心导航、五条主流程、数量四态和原子扣减。

### G6. 建立验证口径

定义未来真实使用需要采集的 Core Outcome、Funnel 与 Diagnostic Metrics，但不伪造基线或目标。

## 5. Non-Goals

V2.0 不解决：

- 食品安全判定、实际保质期或是否可以食用；
- 按食材类别、包装、开封、温度或保存方式设置不同周期；
- AI 图片识别、AI 推荐或生成式菜谱；
- 登录、手机号验证码、云数据库或多设备同步；
- 地图、商圈、外出就餐、真实餐厅或外卖；
- 第三方营养、价格、食品安全或菜谱 API；
- 完整随机菜单采购流程；
- 生产级分析平台或用户画像系统；
- React/Vite 迁移、后端服务或 Pages workflow 改造；
- 重做 V1.0 低保真 Prototype 或移动现有根文档。

## 6. 产品原则

1. **提醒，不判定**：只陈述用户记录的购买日期与已过去天数；
2. **未知保持未知**：缺失、无效或未来日期不猜测、不加权；
3. **硬约束优先**：过敏原/明确不吃、条件、人数、数量四态和补买预算先于购买时长；
4. **解释与规则一致**：界面理由必须来自实际参与加权的批次；
5. **用户最终确认**：批次优先只影响建议顺序，不替用户决定实际使用量；
6. **不提高首录门槛**：购买日期可选，名称仍是唯一必填项；
7. **数据迁移保守**：不从旧字段推断新字段，不以恢复演示数据掩盖迁移失败；
8. **无虚假精度**：天数按本地日历日计算，营养/价格继续明确为估算。

## 7. 购买时长机制

### 7.1 状态定义

| 输入/范围 | 内部状态 | 用户文案 | 推荐权重 | 安全语义 |
|---|---|---|---:|---|
| 当天购买 | `normal` | `今天购买` | 0 | 无 |
| 1–4 天 | `normal` | `购买 N 天` | 0 | 无 |
| 5–6 天 | `prioritize` | `已购买 N 天 · 建议优先使用` | +2 | 日常提醒，不代表临期 |
| ≥7 天 | `long-held` | `已购买 N 天 · 使用前请确认食材状态` | +3 | 不判断过期或安全 |
| 未填写 | `unknown` | `购买时间未知` | 0 | 不猜测 |
| 无效或未来日期 | `unknown` + 输入错误/修正提示 | 编辑时提示修正；已存异常数据按未知展示 | 0 | 不显示负天数 |

`+2/+3` 是 V2.0 的透明、可配置初始规则，不是机器学习评分。真实使用后才能决定是否调整。

### 7.2 计算规则

- `purchasedOn` 使用本地日历日期 `YYYY-MM-DD`；
- `daysSincePurchase` 不写入 LocalStorage，每次显示和推荐时派生；
- 计算按本地“今天”与购买日期的日历日差，不直接用毫秒除以 24 小时，避免夏令时或时区造成偏差；
- 未来日期、格式错误或不存在日期均返回 unknown；
- 日期边界必须支持注入固定“今天”进行测试；
- 一个批次数量为 0 时不参与显示与加权；
- 数量未知的批次可显示购买时长，但不产生购买时长推荐 bonus，直到用户确认存在可用数量；
- 多批次食材分别计算，列表摘要显示最需要关注的已知批次。

### 7.3 食品安全文案边界

允许：

- `已购买 6 天 · 建议优先使用`
- `已购买 8 天 · 使用前请确认食材状态`
- `购买时间未知`
- `购买时长仅供整理库存参考，不能判断食材是否安全。`

禁止：

- `已过期`
- `即将过期`
- `不安全`
- `不能食用`
- `保质期还剩 N 天`
- 任何从购买天数直接推出食品安全结论的图标、颜色或排序说明

## 8. 推荐机制调整

### 8.1 保持不变的主链

```text
用户条件过滤
→ 按人数计算需要量
→ 库存数量四态
→ 补买预算过滤
→ 合格候选集合
→ 透明加权随机
```

购买时长只发生在候选集合已经合格之后，不改变硬约束，也不把“不足”伪装成“满足”。

### 8.2 候选加权规则

1. 保留 V1.0 的数量状态基础权重与近期重复惩罚；
2. 对每个候选，查找菜谱实际需要、单位兼容、已知数量大于 0 的库存批次；
3. 每种食材取可以参与本次制作的最早 `purchasedOn`；
4. 每个候选只取最高一档 age bonus：normal/unknown +0、5–6 天 +2、7+ 天 +3；
5. 不按食材数量叠加多个 bonus，避免“食材越多分越高”压倒库存满足度；
6. 随机结果始终来自合格候选；权重只改变概率，不保证某一道菜必然出现。

### 8.3 推荐理由

当 age bonus 生效时，首要理由格式为：

> 西红柿已购买 6 天，本次优先考虑能够使用它的菜谱。

当存在 ≥7 天批次时追加中性提醒：

> 使用前请按实际保存情况确认食材状态。

当没有可加权批次时，继续使用库存匹配与条件符合理由。界面不显示内部总分，不使用“AI 推荐”“智能判断”或“系统认定安全”。

## 9. 数据模型变化

### 9.1 V1 当前批次

```text
BatchV1
├── id
├── quantity
├── unit
├── precision
├── expiresOn
└── useSoon
```

### 9.2 V2 活跃批次

```text
BatchV2
├── id
├── quantity
├── unit
├── precision
├── purchasedOn: YYYY-MM-DD | null
└── legacy?:
    ├── expiresOn: YYYY-MM-DD | null
    └── useSoon: boolean
```

说明：

- 活跃业务只读取 `purchasedOn`；
- `daysSincePurchase` 与 purchase-age status 是派生值，不存储；
- `legacy` 只用于迁移审计和一个版本周期的兼容，不参与显示、推荐或扣减排序；
- 不新增 `isExpired`、`safeToEat`、`remainingShelfLife` 等字段；
- document `schemaVersion` 从 1 升为 2；
- 主 LocalStorage key 保持 `what-to-eat.portfolio.v1`，避免换 key 造成假性数据丢失；key 名中的 v1 视为既有产品命名，不等同于 schemaVersion。

### 9.3 迁移元信息

V2 document 应记录最小迁移元信息：来源版本、迁移时间、升级说明是否已确认。它用于只展示一次中性提示，不用于分析用户行为。

## 10. LocalStorage Schema Migration

### 10.1 迁移决策

| 旧字段 | V2.0 决策 | 原因 |
|---|---|---|
| `expiresOn` | 从活跃模型废弃，原值保留在 `legacy.expiresOn` | 预计到期日不能可靠代表购买日；保留原始用户输入便于兼容，不参与新逻辑 |
| `useSoon` | 从活跃模型废弃，原值保留在 `legacy.useSoon` | 不能把人工临期标记伪装成购买时长，也不能继续作为 age bonus |
| `purchasedOn` | 新增，可选 | 更容易由用户回忆，支持透明天数提醒 |
| `daysSincePurchase` | 不存储 | 每天会变化，持久化会陈旧 |

### 10.2 迁移步骤

1. 从现有主 key 读取原始字符串，不立即覆盖；
2. 识别 schemaVersion；schema v2 直接校验并加载；
3. 对 schema v1 做结构校验，保留 inventory、pantry、conditions、preferences、session 与 updatedAt；
4. 对每个 batch 新增 `purchasedOn: null`；
5. 把原 `expiresOn/useSoon` 原样移入 `legacy`，不反推日期；
6. 对 pending deduction 保留用户已编辑的 amount、skip、batchId 和单位；旧 `useSoon` 只迁入兼容信息，预览显示“升级前保存的建议，请再次确认批次”，不重新计算或丢弃编辑；
7. 写入一个单代备份 key `what-to-eat.portfolio.backup.schema-v1`；
8. 构建完整 schema v2，执行严格校验；
9. 只有备份和 v2 校验成功后才写入主 key；
10. 重新读取主 key 并校验，成功后进入应用并展示一次升级说明；
11. 任一步失败都保留原主 key，不写演示数据覆盖；页面进入可恢复状态，说明库存尚未升级；
12. “恢复演示数据”需要明确确认，并同时说明会清除当前数据与迁移备份。

### 10.3 迁移后用户体验

一次性中性说明：

> 优先使用提醒已升级为按购买时间计算。原来的到期日期和临期标记没有被当作购买日期；你可以在需要时补充购买时间。

说明可关闭且不阻塞首页。编辑旧批次时，购买日期为空；不得预填原 `expiresOn`。

### 10.4 风险与保护

| 风险 | 影响 | 保护措施 |
|---|---|---|
| 把 expiresOn 当 purchasedOn | 产生错误天数和推荐解释 | 明确禁止推断；新值为 null |
| v2 校验失败触发默认数据 | 用户库存被覆盖 | 迁移失败不调用 reset；保留原主 key与单代备份 |
| 迁移重复运行 | 重复包裹 legacy 或重置日期 | 迁移函数按 schemaVersion 幂等；v2 不再迁移 |
| pending deduction 丢失 | 用户编辑用量消失 | 原样保留编辑；迁移后要求再次确认 |
| 固定 Mock 日期变陈旧 | Demo 永远显示持有很久 | V2.0 Demo 数据按重置日生成相对日期 |
| 日期时区偏移 | 边界状态错误 | 使用本地日历日纯函数与固定 today 测试 |
| legacy 永久滞留 | 数据模型长期负担 | 只承诺保留一个兼容周期；未来版本经人工确认后清理 |

## 11. Change List

### 11.1 P0 — V2.0 发布必须

| 改动 | 当前状态 | 问题 | 新方案 | 用户价值 | 实现影响 | 验收条件 |
|---|---|---|---|---|---|---|
| Schema v2 迁移 | schema v1，v0→v1 简单迁移 | 已发布用户数据可能被新字段校验破坏 | 按第 10 节执行 v1→v2、单代备份、失败不覆盖、幂等迁移 | 升级后库存与编辑不丢失 | `storage.js`、默认数据、pending session、storage tests | 代表性 v1 fixtures 全部迁移；失败时主 key 字节不变；二次加载无再次迁移 |
| 购买日期录入 | 预计到期日期 + 尽快食用复选框 | 难填且暗示安全判断 | 改为可选“购买日期”，最大值为今天；名称仍唯一必填 | 更自然、录入负担可控 | `app.js` 表单、校验、Mock 数据、E2E | 只填名称仍可保存；合法日期刷新后保留；未来/无效日期不能作为有效购买时间 |
| 四档购买时长 | 临期/普通二元提示 | 无法表达未知与持有较久的安全边界 | normal/prioritize/long-held/unknown 四档及固定文案 | 明白提醒依据与不确定性 | 新纯函数模块或现有小模块、UI 状态、CSS | 0/4/5/6/7 天和未知边界全通过；不只靠颜色 |
| 首页与库存表达 | “先吃临期”“预计到期” | 强化错误语义，数量与时长层级混杂 | 数量摘要与购买时长分行；首页显示需优先类数和最早已知购买天数 | 更快识别需要优先考虑的食材 | `app.js`、`styles.css` | 390px/桌面不截断；unknown 不计入优先数；数量四态不被替换 |

## 13. Metrics to Validate

当前没有真实行为数据。以下是未来 Metric Definition，所有 baseline、target 和 trend 均为 TBD。V2.0 规划阶段不引入第三方分析服务。

### 13.1 Core Outcome

**完成一次饮食决策**：用户从一次推荐会话进入菜谱、打开制作确认，并成功提交库存更新。

建议口径：

```text
Decision Completion Rate
= 有 inventory_commit_succeeded 的推荐会话数
÷ 有 recommendation_started 的推荐会话数
```

它是“用户在产品内完成决策”的代理指标，不等同于用户真的吃完、减少浪费或获得营养收益。

### 13.2 Funnel

```text
home_view
→ recommendation_started
→ recommendation_result_shown
→ recipe_viewed
→ cook_preview_opened
→ inventory_commit_succeeded
```

| 指标 | 定义 | 决策用途 | 当前值 |
|---|---|---|---|
| 首页→启动推荐 | `recommendation_started / home_view` | 首页 CTA 与库存提醒是否驱动行动 | TBD |
| 启动→获得结果 | `result_shown / recommendation_started` | 条件和库存是否造成过多无结果 | TBD |
| 结果→菜谱 | `recipe_viewed / result_shown` | 推荐是否值得进一步了解 | TBD |
| 菜谱→制作预览 | `cook_preview_opened / recipe_viewed` | 菜谱是否支持用户做决定 | TBD |
| 预览→库存更新 | `commit_succeeded / cook_preview_opened` | 扣减确认是否造成阻力或建立信任 | TBD |

### 13.3 Diagnostic Metrics

| 指标 | 定义 | 需要避免的误读 | 当前值 |
|---|---|---|---|
| 推荐无结果率 | `no_result / recommendation_started` | 高可能是库存/条件冲突，不一定是算法故障 | TBD |
| 再来一次比例 | `reroll / result_shown` | 可能是趣味探索，也可能是不满意，需要访谈结合 | TBD |
| 库存录入完成率 | 完成至少一个有效批次保存的添加流程 / 开始添加流程 | 不代表库存完整 | TBD |
| 购买日期覆盖率 | 有合法 `purchasedOn` 的活跃批次 / 活跃批次 | 低覆盖可能是可选设计成功降低负担，也可能是字段难填 | TBD |
| 优先食材命中率 | 含 5+ 天已知数量批次的结果 / 存在此类可用库存的推荐会话 | 只衡量规则是否参与，不代表满意 | TBD |
| 优先食材制作转化 | 含 age bonus 结果最终成功制作 / 含 age bonus 结果 | 需要与普通结果对照，不能直接归因 | TBD |
| 优先批次实际扣减率 | 成功扣减 5+ 天批次的制作 / 当时存在可匹配 5+ 天批次的制作 | 扣减是用户确认记录，不等于食材真实被吃完 | TBD |
| 购买时间未知率 | unknown purchase-time 批次 / 活跃批次 | 不应以强制日期降低该数值 | TBD |
| 迁移成功率 | 成功 v1→v2 的本地文档 / 尝试迁移文档 | 没有遥测时只能在测试和用户反馈中观察 | TBD |
| 扣减失败率 | `inventory_commit_failed / cook_preview_opened` | 区分校验失败、存储失败和用户取消 | TBD |
| 重置数据率 | `demo_reset_confirmed / active_local_installations` | 无匿名安装定义前不能可靠计算 | TBD |

## 16. Rollout 与观察建议

当前是非商业化公开 Portfolio，不需要复杂灰度平台。建议：

1. 先用固定 v1 fixtures 和真实浏览器副本做本地迁移演练；
2. 发布前保留当前线上版本的 Git tag/commit 可回退点；
3. 发布 V2.0 后完成一次全新用户与一次 v1 已有数据的线上 smoke；
4. 若出现迁移失败，优先停止写入并保留原数据，不通过 reset 掩盖；
5. 记录真实用户反馈时区分“理解问题、录入负担、推荐满意度、迁移问题”；
6. 没有真实数据前不调整 5/7 天阈值和 +2/+3 权重。
