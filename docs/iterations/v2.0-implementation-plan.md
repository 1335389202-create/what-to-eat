## 1. 冻结决策

### 1.1 不变能力

- 居家闭环：首页 → 库存 → 条件 → 盲盒 → 结果 → 菜谱 → 制作确认 → 扣减 → 更新首页；
- 满足 / 可能满足 / 不足 / 未知数量四态；
- 居家补买总预算及严格库存 / 少量补买；
- 近期推荐惩罚、加权随机、无结果恢复；
- 可编辑/可跳过扣减与整体提交；
- LocalStorage、本地单设备、静态部署、Hash 导航；
- Reduce Motion、移动优先和 GitHub Pages 仓库子路径；
- `prototype/` 76/76 历史资产与 V1.0 执行历史。

### 1.2 新数据与日期契约

- BatchV2 活跃字段：`id`、`quantity`、`unit`、`precision`、`purchasedOn: YYYY-MM-DD | null`、可选 `legacy`。
- `purchasedOn` 是用户本地日历日期，不包含时间和时区；保存前做格式与真实日期校验。
- `daysSincePurchase`、购买时长状态和 bonus 全部实时派生，绝不写入 LocalStorage。
- 使用本地日期组件生成“今天”；日差使用校验后的年月日序数计算，不直接解析 `new Date("YYYY-MM-DD")`，也不以毫秒除 24 小时推断本地自然日。
- future/invalid 均返回 unknown 权重（+0）并携带可区分原因；不产生负天数。
- 购买时长：0–4 天 +0；5–6 天 +2；≥7 天 +3；unknown +0。
- 候选只取最高 bonus；不叠加多个食材。同 bonus 时取 days 更大者，再按菜谱食材顺序和库存批次数组顺序稳定决胜。

### 1.3 Schema v2 与 Load 状态

主 key 保持 `what-to-eat.portfolio.v1`；新增单代备份 key `what-to-eat.portfolio.backup.schema-v1`。`load()` 对调用方暴露可区分结果：

| status | 含义 | 主 key 行为 | 应用行为 |
|---|---|---|---|
| ready | 合法 schema v2 | 不改 | 正常进入 |
| initialized | key 缺失 | 写入默认 v2 | 正常进入 |
| migrated | 合法 v1 已迁移并回读通过 | 写入 v2；备份保留 | 正常进入并显示一次说明 |
| damaged | JSON 无法解析、版本对象损坏或当前 schema 校验失败 | 不自动覆盖 | 阻止写入；说明并提供重试/确认重置 |
| migration-failed | 合法 v1 无法构建/校验 v2 | 原始字节不变 | 阻止写入；重试升级/确认重置 |
| read-failed | storage 读取失败 | 不改 | 保留错误，允许重试 |
| write-failed | 备份、主写入或回读失败 | 写主 key 前不改；写后失败则从备份回滚并验证 | 保留错误与用户编辑，允许重试 |

v1→v2 迁移规则：

1. 保存原始字符串；解析并按源 schema 严格校验；
2. 对合法 v1 先写原始字符串到 backup key；
3. 每个 batch 增加 `purchasedOn: null`；把存在的 `expiresOn` / `useSoon` 原样移入 `legacy`，不推断日期；
4. inventory、pantry、conditions、preferences、session、updatedAt 原样保留；
5. pending deduction 保留 amount、skip、batchId、unit 与用户编辑，旧 useSoon 只留在兼容信息，并标记 `migrationReviewRequired`；
6. 添加最小迁移元信息：`fromSchemaVersion`、`migratedAt`、`upgradeNoticeAcknowledged: false`；
7. 构建、序列化、严格校验 v2 后才写主 key；随后回读校验；
8. 失败时恢复原始主 key；若恢复写入也失败，保留 backup 并进入 write-failed，不宣称已回滚成功；
9. schema v2 重复加载不重复包装 legacy、不改 purchasedOn，迁移幂等；
10. reset 只有在用户明确确认后执行，并清理主 key 与该 schema-v1 备份。

损坏数据和 migration failure 都不自动加载可写演示文档。若需要展示占位内容，必须是只读且不会通过后续 update 覆盖原 key。

**Documentation Impact**

### Step 2 — Purchase-age 领域逻辑

**Goal**

用独立纯函数统一日期解析、日差、四档状态、文案和批次排序，避免推荐、UI、扣减各自计算。

**Files**

- 新增：`src/purchase-age.js`、`tests/purchase-age.spec.mjs`
- 修改：`package.json`（把新测试加入 test / test:unit）

**Changes**

1. 先写边界测试：0、4、5、6、7、>7、unknown、invalid、future、闰日、跨月、跨年、本地午夜前后。
2. 提供小而稳定的接口：`localTodayKey(clock)`、`parseLocalDateKey(value)`、`derivePurchaseAge(purchasedOn, todayKey)`、`purchaseAgeBonus(result)`、`purchaseAgeText(result)`、`compareBatchesByPurchaseDate(a,b,todayKey)`。
3. 解析 YYYY-MM-DD 后做年月日 round-trip 校验；日差用日期组件序数，不使用 UTC 字符串解析结果作为用户日期。
4. future 返回 status unknown、reason future、days null、bonus 0；missing/invalid 原因保持可区分。
5. comparator：合法且不在未来的已知日期升序；其余在后；返回 0 交给稳定排序保留同日期/unknown 原顺序。
6. 函数不读 LocalStorage、不读 DOM、不持久化 daysSincePurchase；todayKey 可注入以实现确定性测试。

**Tests**

Red：`node tests/purchase-age.spec.mjs`。
Green：同命令全部通过。
Regression：`npm run test:unit`，预期 storage、purchase-age、recommender、deduction 全绿。

**Acceptance Criteria**

- 所有边界结果精确符合 +0/+2/+3；
- 本地自然日语义不受 UTC 字符串解析或夏令时 23/25 小时日影响；
- future 不出现负天数，unknown 不加权；
- 文案不含过期/安全结论；
- package test 脚本实际执行新测试。

**Rollback / Risk Notes**

- 日期函数是推荐与扣减的共同依赖；接口稳定后才进入 Step 3/4。
- 若目标浏览器缺少某日期 API，保持手写日历运算，不引入日期库。

**Documentation Impact**

- 对照 PRD 25.2–25.3、Design 32.3–32.4。
- README 不更新。

### Step 3 — 推荐加权与可解释理由

**Goal**

把 V1.0 useSoon +5 完整替换为已批准的购买时长最高档加权，同时保持资格过滤和随机机制。

**Files**

- 修改：`src/recommender.js`、`tests/recommender.spec.mjs`
- 复用：`src/purchase-age.js`
- 原则上不改：`src/data/recipes.js`

**Changes**

1. 先写失败测试：0–4 +0、5–6 +2、≥7 +3、unknown/future +0、多个食材不叠加、只取最高档、同档稳定、近期 .25 惩罚、硬条件、预算、no-result 和 reason。
2. `matchIngredient` 只从单位可兼容、已知数量 >0 且实际能参与本菜谱的 batch 收集 purchase evidence；数量未知可显示日期但不提供 bonus。
3. 严格保持顺序：硬条件 → 人数/库存四态 → stock mode / top-up budget → 为合格候选选择 purchase priority → recent penalty → weighted random。
4. 候选新增可追溯 `purchasePriority`：ingredientId/name、batchId、purchasedOn、days、status、bonus；只保存于运行时。
5. recipe 多食材取最高 bonus；同 bonus 取 days 最大，再按食材与 batch 原顺序，绝不求和。
6. 权重改为 `(statusWeight + purchaseAgeBonus) * repeatPenalty`；删除 hasExpiring/expiringBonus 的活跃计算和理由。
7. bonus 生效时 reason 使用具体食材与天数；≥7 天追加状态确认；无 bonus 沿用库存/条件理由。

**Tests**

Red：`node tests/recommender.spec.mjs`。
Green：同命令全部通过。
Regression：`npm run test:unit`，尤其确认数量四态、补买预算、随机候选与 no-result 原断言仍绿。

**Acceptance Criteria**

- age bonus 不影响候选资格，不把不足改为满足；
- 多批次、多食材、unknown、future 和近期惩罚均有确定性断言；
- reason 与最终使用的 priority evidence 完全一致，不暴露总分；
- 仓库活跃推荐逻辑不再读取 hasExpiring/useSoon。

**Rollback / Risk Notes**

- 权重改变是概率变化，测试应断言权重边界和固定 random 的选择，不做脆弱统计抽样。
- 若候选 API 兼容受影响，优先增加可选 todayKey 参数并保留现有调用顺序，不做大规模重构。

**Documentation Impact**

- 对照 PRD 25.4 与 Prototype 15.2/15.3。
- README 仍不宣称完成。
